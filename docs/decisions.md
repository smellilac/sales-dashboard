# Журнал решений

Каждое решение: статус, что решили, почему, какие варианты отклонили.
Цель — быстро ответить на вопрос «почему здесь сделано именно так?».

## C1 — EF Core migrations вместо Liquibase
**Статус:** settled · 2026-09-24

**Решение:** схема базы управляется EF Core migrations.

**Почему:** задание прямо требует EF Core migrations. Liquibase — стандарт команды, но здесь
он выглядел бы как игнорирование требования.

---

## C2 — Отдельный контейнер для миграций
**Статус:** Draft · 2026-09-24

**Идея:** one-shot контейнер применяет миграции и seed, затем завершается; API стартует после него.
Так код API никогда не выполняет DDL.

**Почему Draft:** для тестового задания это лишний проект и образ. Сейчас выбран DB-INIT.
Вернуться к C2 для production или при нескольких экземплярах API.

## READ-ONLY — API только читает
**Статус:** settled · 2026-09-24

**Решение:** dashboard API только читает данные. Единственная запись — `SalesDbInitializer`.

**Почему:** вывод из задания. Данные появляются только из seed (раздел 4), все блоки — чтение
(разделы 5–6), авторизация и admin panel вне scope (разделы 13, 20).

**Следствия:** тонкий домен без инвариантов записи; `AsNoTracking` везде; индексы влияют только
на чтение; ответы можно кэшировать по конкретным датам (не по названию пресета).

---

## DB-INIT — Миграции и seed при старте API
**Статус:** settled · 2026-09-24

**Решение:** `SalesDbInitializer` (`IHostedService`, async `StartAsync`) вызывает `MigrateAsync`,
затем seed, если таблицы пусты. Включается флагом `Database:ApplyMigrationsOnStartup`, флаг
включён только в docker-compose.

**Почему:** самый простой путь к `docker compose up --build` без ручных шагов; стандартный
подход, проверяющие его узнают.

**Осознанное исключение:** правило команды «код приложения не выполняет DDL». Для одного
экземпляра API в тестовом задании риск принципиальный, не практический. Флаг позволяет
выключить поведение вне docker-compose.

**Отклонено:**
- Отдельный проект Migrator (C2) — лишняя сложность на данном этапе.
- Seed на Python — схема описана в C#; Python-скрипт повторял бы имена таблиц, колонок и формат
  статуса вручную, и компилятор не поймал бы расхождение. Плюс второй runtime в репозитории.

## DB-COMPOSE — PostgreSQL в docker-compose проекта
**Статус:** settled · 2026-09-24

**Решение:** PostgreSQL — сервис в `docker-compose.yml` проекта, с healthcheck
(`pg_isready`). API зависит от него через `depends_on: condition: service_healthy`.

**Почему:** задание требует запуск одной командой без внешних зависимостей. Healthcheck
гарантирует, что `SalesDbInitializer` не начнёт миграции до готовности базы.

## D8 — Vertical Slice Architecture
**Статус:** settled · 2026-09-24

**Решение:** один API-проект, папка на каждый блок dashboard, тонкая папка `Shared`.
Без Clean Architecture слоёв, MediatR и репозиториев.

**Почему:** сквозной логики мало (около 6 правил: период, статусы, деньги по позиции, формулы,
рейтинг, сравнение с прошлым периодом). Домен только читается, слой Domain в CA был бы пустым.
Задание прямо просит не добавлять слои без конкретной проблемы. 6 блоков = 6 slices (совпадает с D9).

**Отклонено:** Clean Architecture и CA + VSA — много маппинга между слоями, которое не решает
никакой проблемы в read-only сервисе.

## D9 — Endpoint на каждый блок
**Статус:** settled · 2026-09-24

**Почему:** каждый блок загружается и падает независимо. Задание требует отдельного
состояния «нет данных по отдельному блоку».

**Отклонено:** один общий endpoint — ошибка одного запроса ломает всю страницу.

## D10 — EF Core по умолчанию, Dapper для особых случаев
**Статус:** settled · 2026-09-24

**Решение:** EF Core LINQ по умолчанию. Dapper — для hot path, сложных запросов и когда
сгенерированный EF Core SQL не устраивает или нужен полный контроль. Один `NpgsqlDataSource`
в DI для обоих — один пул соединений, одна строка подключения.

**Риск:** если одно бизнес-правило (например, «в выручку идут только Paid») записано и в LINQ,
и в SQL-строке Dapper, они могут разойтись. Защита — тест согласованности (open) или
представление в БД (Draft VIEW).

## D12 — Обработка ошибок
**Статус:** settled · 2026-09-24

**Решение:**

# Бизнес-правила

## D1 — Refunded учитывается как Cancelled
**Статус:** settled · 2026-09-24

**Решение:** Refunded не даёт выручки, прибыли и продажи. Отдельная KPI-карточка «Возвраты»:
сумма и доля от Paid + Refunded.

**Почему:** у обоих вариантов есть edge cases, которые в реальном проекте решает PM. Такой
возможности нет, поэтому выбран самый простой и последовательный: одно условие `status = Paid`
во всех блоках, выручка никогда не отрицательная, модель не меняется.

**Отклонено:**
- B: выручка в месяце продажи, минус в месяце возврата — нужен `RefundedAt`, каждый запрос
  работает с двумя датами, выручка менеджера может быть отрицательной.
- Игнорировать возврат — показывает деньги, которых у компании нет.

**Известный минус A:** в системе с живыми данными цифры месяца продажи уменьшаются задним
числом. У нас данные неизменны после seed, поэтому на практике не проявляется.

---

## D2 — Продажа = Paid
**Статус:** settled · 2026-09-24

**Решение:** количество продаж = число Paid; средний чек = выручка / число Paid, по сделкам.
Таблица последних продаж показывает все статусы, суммы Cancelled/Refunded — серые, вне итогов.

**Почему:** сделки без денег занижали бы средний чек. Отмены — отдельная проблема, её видно
в таблице и в карточке «Возвраты».

---

## D3 — Предыдущий период
**Статус:** settled · 2026-09-24

**Решение:** API принимает только `from`/`to`. Предыдущий период — окно той же длины сразу
перед выбранным, всегда. Считает сервер, в ответе — даты обоих периодов.

**Почему:** одно правило для всех пресетов, одно место в коде, легко тестировать и описать.

**Цена решения:** «этот месяц» (01.09–24.09) сравнивается с 08.08–31.08, а не с 01.08–24.08.

**Следствие:** пресеты в даты превращает frontend, в бизнес-часовом поясе, а не в поясе
браузера.

**Отклонено:** год к году — в seed 12 месяцев, сравнения были бы пустыми; календарные месяцы
целиком — неполный текущий месяц всегда «падает».

---

## D4 — Даты и часовой пояс
**Статус:** settled · 2026-09-24

**Решение:** `SoldAt` — `timestamptz` в UTC. Дни считаются в `ReportingOptions.TimeZone`
(Europe/Moscow по умолчанию). `from`/`to` — `DateOnly` включительно, сервер превращает их
в полуоткрытый диапазон `[from 00:00, to+1 00:00)` по бизнес-поясу, затем в UTC.
Валидация `from ≤ to`, не больше 2 лет — через `ErrorOr`. `TimeProvider` через DI.

**Почему:** продажа в 01:30 по Москве иначе попала бы во вчерашний день по UTC.
Полуоткрытый диапазон даёт каждой секунде ровно один день — закрывает edge case «продажа на
границе периода». В Москве нет перехода на летнее время.

**Отклонено:** `<= 23:59:59` — теряет продажи в последнюю секунду дня.

## D5 — Деньги, копии цен, версия продукта
**Статус:** settled · 2026-09-24

**Решение:**
- `numeric(18,2)` / `decimal` для цены и себестоимости.
- `SaleItem` хранит копии `unit_price`, `unit_cost` и `product_version_at` на момент продажи.
- Generated columns (STORED): `line_revenue = quantity × unit_price`,
  `line_cost = quantity × unit_cost`.
- `Product.VersionAt` (`timestamptz`) — с какого момента действует карточка товара.
- `SaleItem.Id` — UUID v7 без бизнес-смысла (см. IDS).
- Округление только на экране; маржа отдаётся долей.

**Почему:**
- `decimal` точен; `double` даёт расхождения в копейках между блоками.
- Два знака достаточно; `numeric(18,4)` — лишнее.
- Копия как в чеке: изменение цены или себестоимости товара не меняет прошлые сделки.
- Generated columns держат формулу позиции в одном месте для EF Core и Dapper.
- Версия как момент времени упорядочена, уникальна для товара и говорит «с какого момента»,
  без отдельной таблицы.
- Версия в отдельной колонке, не в Id: ключ не должен нести смысл, иначе при смене правила
  версионирования меняются ключи и ссылки на них.

**Отклонено:**
- `bigint` в копейках — конверсии ×100 и /100 везде, риск ошибки без выгоды.
- Брать цену из `Product` — прошлые сделки меняются задним числом.
- Таблица истории цен — join по диапазону дат в каждом агрегатном запросе, больше I/O и
  риск неверной маржи при пересекающихся диапазонах.

**Ограничение:** по `product_version_at` нельзя посмотреть старую карточку — только понять,
что она была другой (см. Draft PRODUCT-HISTORY).

## D7 — Рейтинг
**Статус:** settled · 2026-09-24

**Решение:** спортивная нумерация (1, 1, 3); порядок метрика → выручка → имя. Менеджеры без
продаж — внизу, без места, «Нет продаж». Неактивные без продаж скрыты. «Лучший менеджер» —
первый по валовой прибыли; при равенстве «и ещё N с тем же результатом».

**Почему:** равные результаты получают равное место; стабильный порядок строк не «прыгает»
при обновлении; менеджер без продаж — важная для руководителя информация.

## IDS — UUID v7 для всех ключей
**Статус:** settled · 2026-09-24

**Решение:** все первичные ключи — `uuid`, значения UUID v7 (`Guid.CreateVersion7()`).

**Почему:** задел на масштабирование — Id можно создавать вне базы (несколько источников,
импорт, шардирование) без конфликтов. Версия 7 упорядочена по времени, поэтому вставки
идут в конец B-tree индекса, как у `bigint`.

**Цена:** ключ 16 байт вместо 8; в логах и URL длиннее.

**Отклонено:** `bigint identity` — компактнее, но Id создаёт только база. UUID v4 —
случайный порядок вставок фрагментирует индекс.

---

## ENUMS — Enum в модели + строка и CHECK в базе
**Статус:** settled · 2026-09-24

**Решение:** `SaleStatus` и `CustomerSegment` — C# enum. В БД хранятся строкой
(`HasConversion<string>()`) с `CHECK`-ограничением. Список значений в `CHECK` строится из
enum через `Enum.GetNames<T>()`:

```csharp
builder.ToTable(t => t.HasCheckConstraint(
    "ck_sales_status",
    $"status IN ({string.Join(", ", Enum.GetNames<SaleStatus>().Select(n => $"'{n}'"))})"));
```

**Почему строка:** `WHERE status = 'Paid'` читается без справочника; изменение порядка
значений в enum не меняет смысл старых данных. Разница в размере на нашем объёме не видна.

**Почему и модель, и CHECK:** это два уровня защиты.
- Enum защищает записи через наш код, но не полностью: `(SaleStatus)7` — корректный C#,
  и EF Core запишет `'7'`.
- `CHECK` защищает базу от любого писателя: Dapper, psql, будущий импорт, другое приложение.
- Без `CHECK` плохое значение всплывает при чтении — падает endpoint далеко от места ошибки.
  С `CHECK` падает сама запись, сразу.

**Почему из enum:** один источник правды. Новое значение в enum — и
`dotnet ef migrations add` сам покажет изменение ограничения.

**Честная оценка:** у нас один писатель и неизменные данные, поэтому это дешёвая страховка,
а не необходимость.

**Отклонено:**
- Число (по умолчанию в EF Core) — нечитаемо в SQL, смена порядка enum ломает данные.
- Нативный enum PostgreSQL (`CREATE TYPE`) — добавление значения требует отдельной миграции
  с ограничениями.

## NAMING — snake_case в базе
**Статус:** settled · 2026-09-24

**Решение:** snake_case через `EFCore.NamingConventions`.

**Почему:** в PostgreSQL имена в PascalCase нужно брать в кавычки (`"SoldAt"`), что делает
Dapper-запросы шумными и ломкими. snake_case — привычный формат PostgreSQL.

**Оговорка:** нет информации о практиках команды по именованию. Нет желания тянуть в проект
много пакетов, но этот пакет решает конкретную проблему одной строкой настройки. Если у
команды другой стандарт — пересмотреть.

---

## API-KPI — Форма KPI-ответа
**Статус:** settled · 2026-09-24

**Решение:** каждая метрика — `current`, `previous`, `change`. Для денег и количества
`change` — относительное изменение (0.12 = +12%). Для маржи — отдельное поле
`changePoints` — разница в процентных пунктах. В ответе `period` и `previousPeriod`.

**Почему:** рост маржи с 20% до 22% — это +2 п.п., а не +10%. Разные поля не дают frontend
их перепутать.

## TIMESERIES — Шаг графика выбирает сервер
**Статус:** settled · 2026-09-24

**Решение:** ≤ 31 дня — день, ≤ 180 — неделя (с понедельника), иначе месяц. Неполные

**Почему:** график всегда читаемый, frontend проще. Параметр можно добавить позже без
поломки контракта.

**Отклонено:** шаг от клиента — можно запросить 730 точек за 2 года.

## RECENT-SALES — Keyset-пагинация
**Статус:** settled · 2026-09-24

**Решение:** keyset (cursor) по (`sold_at` desc, `id` desc); курсор непрозрачный
(base64 от пары значений). Страница 20, максимум 100. UI — кнопка «Показать ещё».

**Почему:** пагинация нужна для read-heavy системы. Keyset, а не offset: `OFFSET 10000`
заставляет базу прочитать и выбросить 10 000 строк, а keyset всегда читает только
следующую страницу. Второй ключ `id` делает порядок стабильным при одинаковом `sold_at`.

**Цена:** нельзя перейти сразу на страницу N — для ленты последних продаж это не нужно.

## RANKING-CHANGE — Изменение метрики, не места
**Статус:** settled · 2026-09-24

**Решение:** в рейтинге изменение к прошлому периоду — по прибыли (или выбранной метрике).
Изменение места — Draft (RANK-POSITION-CHANGE).

**Почему:** изменение места требует посчитать рейтинг прошлого периода с теми же правилами
равенства — больше работы и edge cases.

## OPENAPI — Встроенный OpenAPI + сгенерированные типы
**Статус:** settled · 2026-09-24

**Решение:** `Microsoft.AspNetCore.OpenApi` (встроен в .NET 10), документ генерируется при
сборке и коммитится в репозиторий. UI для просмотра — Scalar. Типы для frontend —
`openapi-typescript` из закоммиченного документа.

**Почему:** контракт backend и frontend не расходится. Закоммиченный документ позволяет
собирать frontend без запущенного backend. Встроенный генератор — меньше пакетов, чем
Swashbuckle, который шаблоны .NET больше не включают.

## CONSISTENCY-TEST — Тест согласованности сумм
**Статус:** settled · 2026-09-24

**Решение:** интеграционный тест: сумма точек динамики = сумма по категориям = сумма по
рейтингу = выручка KPI, для нескольких периодов.

**Почему:** ловит расхождение правил между LINQ и SQL, откуда бы оно ни взялось. Проверяет
то же, что проверяющие будут делать руками.

## D13 — Seed
**Статус:** settled · 2026-09-24

**Решение:** см. раздел Seed в `Claude.md`.

**Почему даты от дня запуска:** при фиксированной дате через месяц «последние 7 дней» были
бы пустыми. Форма данных при этом воспроизводима благодаря фиксированному зерну.

**Почему edge cases не в seed:** подгонка случайных данных под «два менеджера с одинаковым
результатом» хрупкая. Такие случаи надёжнее проверять тестами на маленьких ручных наборах.

**Детерминированные Id:** `Guid.CreateVersion7()` использует текущее время и случайные байты,
поэтому после пересоздания БД Id были бы новыми. `SeedGuid` строит UUID v7 по RFC 9562 из
seeded-генератора — пересоздание даёт те же Id (при том же дне запуска), а порядок Id продаж
совпадает с порядком `SoldAt`.

## REPO — Monorepo `sales-dashboard`
**Статус:** settled · 2026-09-24

**Решение:** один репозиторий `sales-dashboard`: `backend/`, `frontend/`, `docker-compose.yml`,
`Claude.md`, `docs/`, `README.md`, `AI_NOTES.md` в корне. В `docker-compose.yml` задано
`name: sales-dashboard`.

**Почему monorepo:** задание ожидает одну ссылку со структурой `/frontend`, `/backend`,
`docker-compose.yml`. Одна команда запуска без submodules. Изменение API-контракта —
один атомарный коммит: endpoint, `openapi.json` и TypeScript-типы не могут разойтись.

**Почему такое имя:** совпадает с .NET-неймспейсом `SalesDashboard`; нейтральное (без
названия компании), описывает, что это, а не для кого. `name:` в compose не зависит от
имени папки, в которую клонировали репозиторий.

**Отклонено:** отдельные репозитории — два клона, submodules, синхронизация контракта между
репозиториями, разорванная история коммитов.

## DOCS — Урезанный набор документации для Claude Code
**Статус:** settled · 2026-09-24

**Решение:** в этом проекте используются только два файла:
- `Claude.md` — главный рабочий документ;
- `docs/decisions.md` — журнал решений (этот файл).

**Почему:** 8-часовой timebox и маленький размер проекта. Полный набор документов занял бы
заметную часть времени, а большинство разделов для этого сервиса были бы пустыми или
очевидными (нет брокеров, кэшей, Kubernetes, межсервисного взаимодействия).

**Обычный формат (для сервисов в реальной работе), нужен для корректного prompt engineering:**

| Файл | Содержание |
|---|---|
| `Claude.md` | Главный рабочий документ сервиса, в корне проекта. Ответственность сервиса, tech stack, settled архитектурные решения (не переоткрывать), Draft-пункты, ключевые invariants и правила кода. Claude Code читает его первым при каждой задаче. |
| `docs/architecture.md` | Структура проекта, слои, порядок DI-регистрации, интерфейсы ключевых компонентов. |
| `docs/conventions.md` | Соглашения по коду: именование классов и констант, правила логирования, структура тестов, что никогда не должно появляться в коде. |
| `docs/data-layer.md` | Что сервис читает и пишет: базы данных, таблицы, брокеры, TTL кэшей, форматы ключей. |
| `docs/development.md` | Локальный запуск, шаги CI/CD, Docker-образы, Kubernetes-манифесты, как добавить новую фичу. |
| `docs/domain.md` | Бизнес-контекст: сущности домена, их поведение, бизнес-правила. |
| `docs/infrastructure.md` | Конфигурация внешних зависимостей: брокеры, кэши, базы данных, retry-политики, health checks. |
| `docs/observability.md` | OpenTelemetry wiring, метрики, structured logging, реализация health checks, полезные запросы для мониторинга. |
| `docs/service-boundaries.md` | Чем сервис владеет, что только читает, что никогда не делает, правила межсервисного взаимодействия. |
| `docs/application-contracts.md` | Wire contracts: поля, типы, nullable/required, почему существует каждое поле. |

**Где это содержимое сейчас:** домен, бизнес-правила, модель данных, API-контракты,
соглашения по коду и границы сервиса (READ-ONLY) — разделы `Claude.md`. Причины решений —
здесь. Запуск и описание API — будущий `README.md` (требование задания).

**Отличие от обычного формата:** `docs/decisions.md` в стандартном наборе нет. Он добавлен,
потому что проверяющие будут спрашивать «почему сделано именно так?», и ответ должен быть
записан, а не восстановлен по памяти.
