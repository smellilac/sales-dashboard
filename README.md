# Sales Performance Dashboard

Дашборд аналитики продаж менеджеров (B2B) — тестовое задание DJI-Market.ru. Менеджеры продают
компаниям-клиентам; дашборд показывает выручку, прибыль, маржу, рейтинг менеджеров, динамику,
топ товаров и ленту последних продаж за выбранный период с сравнением к предыдущему. Backend —
.NET 10 (ASP.NET Core Minimal APIs, EF Core + Dapper, PostgreSQL), frontend — React + TypeScript,
всё поднимается одной командой через Docker Compose.

## 1. Что это

Дашборд для руководителя отдела продаж: за выбранный период он видит ключевые метрики (выручка,
валовая прибыль, маржа, средний чек, число продаж, возвраты, лучший менеджер), рейтинг менеджеров,
динамику по времени, разбивку по категориям, топ-10 товаров и ленту последних продаж.

Стек: **.NET 10** (ASP.NET Core Minimal APIs, EF Core + Npgsql, Dapper), **PostgreSQL 17**,
**React + TypeScript** (Vite, TanStack Query, Tailwind + shadcn/ui, Recharts), **Docker Compose**.
Timebox задания — 8 часов; цель — запуск одной командой.

## 2. Запуск

**Требования:** Docker Engine ≥ 20.10 и Docker Compose v2 (команда `docker compose`, не
`docker-compose`). Больше ничего ставить не нужно — PostgreSQL, backend и frontend поднимаются
как сервисы, .NET SDK и Node ставить локально не требуется.

**Одна команда** (из корня репозитория):

```bash
docker compose up --build
```

**Адреса после старта:**

| Что | URL |
|---|---|
| Дашборд | http://localhost:3000 |
| API | http://localhost:8080 |
| Scalar (интерактивная документация API) | http://localhost:8080/scalar |
| OpenAPI JSON | http://localhost:8080/openapi/v1.json |

Scalar и OpenAPI отдаются напрямую с порта API (8080); nginx на порту 3000 проксирует на backend
только пути `/api/*`.

**Сколько ждать при первом запуске.** Первая сборка образов занимает несколько минут (скачивание
базовых образов, `npm ci` + Vite-сборка frontend, `dotnet publish` backend). После сборки API при
первом старте применяет миграции и заполняет базу (seed) — на это заложен запас в healthcheck
(`start_period: 40s`). Frontend стартует только после того, как API отдаёт `200` на
`/health/ready`, поэтому открытый дашборд сразу видит готовый API. Повторные запуски быстрее:
образы уже собраны, база сохраняется в volume и seed не повторяется (таблицы уже не пусты).

**Остановить** (Ctrl+C, затем):

```bash
docker compose down
```

**Сбросить данные** — удалить контейнеры вместе с volume базы; при следующем `up` миграции и seed
выполнятся заново:

```bash
docker compose down -v
```

## 3. Если не запускается

- **Заняты порты 3000 или 8080.** Compose публикует наружу только их (порт PostgreSQL наружу не
  выставлен). Если порт занят другим процессом — освободите его или измените левую часть проброса
  в `docker-compose.yml` (например, `"3001:80"`), затем `docker compose up --build`.
- **Windows и переводы строк (CRLF).** Если репозиторий клонирован с автоконвертацией `core.autocrlf`,
  shell-скрипты и конфиги могут получить `\r\n` и ломаться внутри Linux-контейнеров. Клонируйте с
  `git config core.autocrlf false` или конвертируйте файлы в LF.
- **Старый Docker без `compose` v2.** Команда `docker compose` (с пробелом) — часть Docker Compose v2.
  На старых установках есть только `docker-compose` (с дефисом) — обновите Docker Desktop / Docker
  Engine до актуальной версии.

## 4. Архитектура

**Связь сервисов:** браузер → **frontend (nginx, порт 3000)** → проксирует `/api/*` →
**API (.NET, порт 8080)** → **PostgreSQL**. Frontend и API живут на одном origin (nginx проксирует
API), поэтому CORS не нужен. API зависит от готовности PostgreSQL (`depends_on: service_healthy`),
frontend — от готовности API. PostgreSQL наружу не публикуется.

**Vertical Slice Architecture.** Backend — один проект, папка на каждый блок дашборда
(`Features/Kpi`, `Features/ManagerRanking`, `Features/Timeseries`, `Features/Categories`,
`Features/TopProducts`, `Features/RecentSales`) плюс тонкий `Shared`. **Без Clean Architecture,
MediatR и репозиториев:** сервис только читает данные, сквозной логики мало (период, статусы,
формулы, рейтинг, сравнение с прошлым периодом), слой Domain был бы пустым, а маппинг между слоями
не решал бы никакой проблемы. Подробнее — [D8 в `docs/decisions.md`](docs/decisions.md#d8--vertical-slice-architecture).

**Структура репозитория** (до второго уровня):

```
sales-dashboard/
├── backend/
│   ├── src/            # SalesDashboard.Api — единственный API-проект (Features/, Data/, Shared/)
│   ├── tests/          # SalesDashboard.Api.Tests — xUnit v3 + Testcontainers
│   ├── openapi/        # закоммиченный OpenAPI-документ (SalesDashboard.Api.json)
│   └── Dockerfile
├── frontend/
│   ├── src/            # React + TypeScript (api/, components/, features/, period/, test/)
│   ├── public/
│   ├── nginx.conf      # отдаёт статику, проксирует /api → api:8080
│   └── Dockerfile
├── docs/
│   └── decisions.md    # журнал решений (почему сделано именно так)
├── docker-compose.yml  # postgres + api + frontend, name: sales-dashboard
├── Claude.md           # рабочий документ проекта: инварианты и settled-решения
├── AI_PROMPTS.md       # промпты, использованные при разработке
├── README.md
└── LICENSE
```

## 5. API

Все endpoints — `GET` под префиксом `/api/dashboard`, принимают период `from`/`to` (даты `YYYY-MM-DD`,
включительно). Полный контракт — в [OpenAPI-документе](backend/openapi/SalesDashboard.Api.json) и в
Scalar.

| Endpoint | Параметры | Что возвращает |
|---|---|---|
| `/api/dashboard/kpis` | `from`, `to` | KPI-карточки: выручка, валовая прибыль, число продаж, средний чек, маржа, возвраты, лучший менеджер; для каждой метрики `current`/`previous`/`change`, плюс `period` и `previousPeriod`. |
| `/api/dashboard/managers/ranking` | `from`, `to`, `rankBy` | Рейтинг менеджеров. `rankBy` = `grossProfit` (по умолчанию) или `averageCheck`. Для каждой строки — место, метрики и изменение метрики к прошлому периоду. |
| `/api/dashboard/timeseries` | `from`, `to` | Точки динамики (выручка, прибыль, число Paid-продаж) с шагом, который выбирает сервер; поле `granularity`. |
| `/api/dashboard/categories` | `from`, `to` | По каждой категории: выручка, прибыль, маржа, единицы, доля в выручке. |
| `/api/dashboard/products/top` | `from`, `to` | 10 товаров с наибольшей валовой прибылью: выручка, прибыль, маржа, единицы. |
| `/api/dashboard/sales/recent` | `from`, `to`, `limit`, `cursor` | Лента последних продаж (все статусы). Keyset-пагинация (см. ниже). |

**Формат ошибок.** Один формат для всех ошибок — `ProblemDetails` (RFC 9457,
`application/problem+json`). Ожидаемые ошибки (например, невалидный период или неверный `rankBy`)
внутри собираются через `ErrorOr` и общим маппингом превращаются в `ProblemDetails`; ошибки
валидации — `HttpValidationProblemDetails` с полем `errors`. Инфраструктурные исключения ловит
глобальный обработчик и тоже отдаёт `ProblemDetails` (плюс лог Serilog). Подробнее —
[D12](docs/decisions.md#d12--обработка-ошибок).

**Keyset-пагинация последних продаж.** Курсор — по паре (`sold_at` desc, `id` desc), непрозрачный
(Base64Url от пары значений). Размер страницы `limit` по умолчанию 20, диапазон 1..100. В ответе —
`items` и `nextCursor` (или `null`, если страниц больше нет); следующую страницу запрашивают,
передав `cursor=<nextCursor>`. Второй ключ `id` делает порядок стабильным при одинаковом `sold_at`.
Offset не используется: keyset всегда читает только следующую страницу. Подробнее —
[RECENT-SALES](docs/decisions.md#recent-sales--keyset-пагинация).

## 6. Бизнес-правила

**Формулы (деньги живут только в позициях чека `SaleItem`):**

| Метрика | Определение |
|---|---|
| Revenue (выручка) | Сумма `line_revenue` (= `quantity × unit_price`) по позициям **только Paid**-сделок. |
| Gross Profit (валовая прибыль) | Сумма `line_revenue − line_cost` по позициям Paid-сделок. |
| Margin (маржа) | `Gross Profit / Revenue`, доля; `null`, если выручки нет. |
| Average Check (средний чек) | `Revenue / (число Paid-сделок)`, по сделкам, а не по позициям; `null`, если продаж нет. |
| Sales count (число продаж) | Количество **Paid**-сделок. |

**Статусы сделок.** `Paid` / `Cancelled` / `Refunded`.

- **Paid** — единственный статус, дающий выручку, прибыль и продажу.
- **Cancelled** — не даёт ничего.
- **Refunded** — учитывается как Cancelled: **не даёт** выручки, прибыли и продажи. Для возвратов
  есть отдельная KPI-карточка «Возвраты»: сумма и доля от `Paid + Refunded`.

**Почему возвраты именно так (вариант A) и что это решение за PM.** У каждого варианта учёта
возвратов есть свои edge cases, которые в реальном проекте закрывает product-менеджер. Такой
возможности в задании нет, поэтому осознанно выбран самый простой и последовательный вариант: одно
условие `status = Paid` во всех блоках, выручка никогда не отрицательная, модель данных не меняется.
Отклонён вариант B (выручка в месяце продажи, минус в месяце возврата) — он требует поля `RefundedAt`,
работы с двумя датами в каждом запросе и допускает отрицательную выручку менеджера. Известный минус
варианта A (цифры месяца продажи уменьшаются задним числом) у нас не проявляется: данные неизменны
после seed. Подробнее — [D1](docs/decisions.md#d1--refunded-учитывается-как-cancelled),
[D2](docs/decisions.md#d2--продажа--paid).

**Таблица последних продаж** показывает сделки всех статусов; суммы Cancelled/Refunded серые и не
входят в итоги.

**Предыдущий период.** API принимает только `from`/`to`. Предыдущий период — окно **той же длины
сразу перед выбранным**, всегда (в том числе для «этого месяца»). Считает сервер и возвращает даты
обоих периодов. Пример: «этот месяц» `01.09–24.09` сравнивается с `08.08–31.08` (те же 24 дня
подряд), а не с `01.08–24.08`. Одно правило для всех пресетов — одно место в коде и предсказуемое
сравнение. Подробнее — [D3](docs/decisions.md#d3--предыдущий-период).

**Границы дат и часовой пояс.** `sold_at` хранится как `timestamptz` в UTC. Дни считаются в бизнес-часовом
поясе (`Europe/Moscow` по умолчанию). `from`/`to` — включительные даты; сервер превращает их в
полуоткрытый диапазон `[from 00:00, to+1 00:00)` в бизнес-поясе и переводит в UTC. Полуоткрытый
диапазон отдаёт каждой секунде ровно один день (продажа на границе периода не теряется и не
дублируется). Валидация: `from ≤ to` и период не длиннее 2 лет. Пресеты (`7d` и т. п.) в даты
превращает frontend — в бизнес-поясе, а не в поясе браузера. Подробнее —
[D4](docs/decisions.md#d4--даты-и-часовой-пояс).

**Деление на ноль.** Маржа и средний чек — `null`, если нет выручки/продаж (UI показывает «—»).
Изменение к прошлому периоду — `null`, если в прошлом периоде было 0 (UI: «нет данных для
сравнения»). 0 % и «нет данных» — это разные факты. Подробнее —
[D6](docs/decisions.md#d6--деление-на-ноль).

**Рейтинг и равенство.** Спортивная нумерация (1, 1, 3). Порядок сортировки: метрика → выручка →
имя. Менеджеры без продаж — внизу, без места, с пометкой «Нет продаж»; неактивные без продаж скрыты.
«Лучший менеджер» — первый по валовой прибыли; при равенстве — «и ещё N с тем же результатом».
В рейтинге изменение к прошлому периоду считается по метрике (прибыли), а не по месту. Подробнее —
[D7](docs/decisions.md#d7--рейтинг), [RANKING-CHANGE](docs/decisions.md#ranking-change--изменение-метрики-не-места).

**Копии цен в позициях.** `SaleItem` хранит копии `unit_price`, `unit_cost` и `product_version_at`
на момент продажи (как строка в бумажном чеке). Поэтому изменение цены или себестоимости товара не
меняет прошлые сделки. `line_revenue` и `line_cost` — generated columns (STORED), формула позиции
живёт в одном месте. Подробнее — [D5](docs/decisions.md#d5--деньги-копии-цен-версия-продукта).

## 7. Данные и seed

Seed выполняется при старте API, только если таблицы пусты. Объёмы: **20 менеджеров, 80 клиентов,
6 категорий, ~40 товаров, ~4 000 сделок за 12 месяцев**, 1–4 позиции в сделке.

**Профили менеджеров** (чтобы рейтинг и KPI были осмысленными): 3 сильных, 3 слабых, 2 «крупные
сделки», 2 «много мелких», 1 в отпуске 6 недель, 1 неактивный (уволен 3 месяца назад), остальные
средние.

**Сезонность:** пик март–май и декабрь, спад в январе. Отмены — 5–8 %, возвраты — 3–5 %, плюс
3–5 очень крупных сделок. В середине года — обновление прайса: у части товаров новая цена и новый
`version_at`.

**Воспроизводимость.** Bogus с фиксированным локальным зерном (`Randomizer(20260924)`); Id
детерминированные — `SeedGuid` строит UUID v7 по RFC 9562 из seeded-генератора, поэтому пересоздание
базы даёт те же Id (при том же дне запуска), а порядок Id продаж совпадает с порядком `sold_at`.
Даты продаж — смещения **от дня запуска**, а не от фиксированной даты: иначе через месяц «последние
7 дней» оказались бы пустыми. Форма данных при этом остаётся воспроизводимой. Сложные edge cases
(равенство менеджеров, продажа в полночь) в seed не закладываются — они проверяются тестами на
маленьких ручных наборах. Подробнее — [D13](docs/decisions.md#d13--seed).

## 8. Технические решения и индексы

- **EF Core и Dapper.** EF Core LINQ — по умолчанию (`AsNoTracking`, сервис только читает). Dapper —
  для hot path и сложных запросов, когда нужен полный контроль над SQL. Один `NpgsqlDataSource` в DI
  общий для обоих — один пул соединений, одна строка подключения. Риск расхождения одного правила в
  LINQ и SQL закрыт тестом согласованности (см. раздел 9).
  [D10](docs/decisions.md#d10--ef-core-по-умолчанию-dapper-для-особых-случаев).
- **Generated columns.** `line_revenue` и `line_cost` — вычисляемые колонки STORED, формула позиции
  в одном месте для EF Core и Dapper. [D5](docs/decisions.md#d5--деньги-копии-цен-версия-продукта).
- **CHECK из enum.** `SaleStatus` и `CustomerSegment` — C# enum, в БД хранятся строкой
  (`HasConversion<string>()`) с `CHECK`-ограничением, список значений которого строится из enum через
  `Enum.GetNames<T>()` — один источник правды, без ручного дублирования.
  [ENUMS](docs/decisions.md#enums--enum-в-модели--строка-и-check-в-базе).
- **UUID v7.** Все первичные ключи — `uuid` (`Guid.CreateVersion7()`): упорядочены по времени, поэтому
  вставки идут в конец B-tree индекса; Id можно создавать вне базы. [IDS](docs/decisions.md#ids--uuid-v7-для-всех-ключей).
- **snake_case.** Имена в БД — snake_case через `EFCore.NamingConventions`: избавляет Dapper-запросы
  от кавычек вокруг `"PascalCase"`. [NAMING](docs/decisions.md#naming--snake_case-в-базе).
- **Миграции и seed при старте.** `SalesDbInitializer` (`IHostedService`) применяет EF Core migrations
  и затем seed. Включается флагом `Database:ApplyMigrationsOnStartup`, который включён только в
  docker-compose. Это единственное место, где API выполняет DDL/запись.
  [DB-INIT](docs/decisions.md#db-init--миграции-и-seed-при-старте-api).

**Индексы сейчас** (из миграции `InitialSchema`) — индексы на внешние ключи и уникальный на `sku`:

| Индекс | Таблица (колонки) | Тип |
|---|---|---|
| `ix_products_category_id` | `products (category_id)` | FK |
| `ix_products_sku` | `products (sku)` | уникальный |
| `ix_sale_items_product_id` | `sale_items (product_id)` | FK |
| `ix_sale_items_sale_id` | `sale_items (sale_id)` | FK |
| `ix_sales_customer_id` | `sales (customer_id)` | FK |
| `ix_sales_manager_id` | `sales (manager_id)` | FK |

**Индексов под чтение по периоду пока нет.** Кандидаты (индекс по `sales.sold_at` для фильтра по
периоду, составной `(sold_at, id)` под keyset-пагинацию последних продаж, возможно
`(manager_id, sold_at)` под рейтинг) сознательно отложены в отдельную ветку `perf` и будут
добавляться только после проверки через `EXPLAIN ANALYZE` на реальных запросах — чтобы индексы
подтверждались планами, а не догадками. Подробнее — [D11](docs/decisions.md#d11--индексы),
[PERF](docs/decisions.md#perf--отдельная-ветка-для-оптимизации-чтения).

## 9. Тесты

**Backend** (`backend/tests/SalesDashboard.Api.Tests`, xUnit v3 + Testcontainers) — интеграционные
тесты каждого endpoint на реальном PostgreSQL в контейнере, тесты периода/часового пояса, маппинга
ошибок, глобального обработчика исключений, health-checks, схемы, seed и OpenAPI-документа. Отдельно —
**тест согласованности** (`ConsistencyTests`): для нескольких периодов проверяет, что сумма точек
динамики = сумма по категориям = сумма по рейтингу = выручка KPI. Он ловит расхождение бизнес-правил
между LINQ и SQL. [CONSISTENCY-TEST](docs/decisions.md#consistency-test--тест-согласованности-сумм).

Запуск (нужен **работающий Docker** — тесты поднимают PostgreSQL через Testcontainers):

```bash
cd backend
dotnet test
```

**Frontend** (`frontend/src`, Vitest + Testing Library) — тесты блоков дашборда с моками API. Запуск:

```bash
cd frontend
npm ci
npm test
```

Frontend-тесты Docker не требуют.

## 10. Как проверить edge cases руками

После `docker compose up --build` откройте дашборд (http://localhost:3000) и попробуйте:

- **Пустой период / слишком большой диапазон.** Задайте произвольный диапазон длиннее 365 дней —
  сервер вернёт ошибку валидации (`ProblemDetails`): период не длиннее 2 лет. Задайте узкий диапазон,
  в котором продаж нет — блоки покажут состояние «нет данных».
- **Менеджер в отпуске.** В seed есть менеджер, не продававший 6 недель. Выберите период внутри его
  отпуска — он не даёт продаж за этот период (в рейтинге — внизу, «Нет продаж»).
- **Неактивный менеджер.** Есть менеджер, уволенный 3 месяца назад. Неактивные без продаж в выбранном
  периоде в рейтинге скрыты.
- **Ошибка API.** Остановите backend и обновите страницу — каждый блок покажет своё состояние ошибки
  независимо (endpoint на блок, D9), страница целиком не падает:

  ```bash
  docker compose stop api
  ```

  Вернуть: `docker compose start api`.

**Только автотестами** проверяются случаи, которые не закладываются в seed (их подгонка под случайные
данные хрупкая): **равенство менеджеров** в рейтинге и **продажа в полночь** на границе периода — см.
тесты рейтинга и периода в `backend/tests/SalesDashboard.Api.Tests` (`RankingEndpointTests`,
`ReportingPeriodTests`). Причина — [D13](docs/decisions.md#d13--seed).

### Известные проблемы графика «Динамика продаж»

Данные графика верные — значения в подсказке при наведении совпадают с API, проблемы только в
отображении.

- **Подписи оси X показывают «undefined» и наезжают друг на друга.** Функция форматирования подписи
  получает строку `bucketStart`, а ожидает другой тип, и число подписей ничем не ограничено.
  *Как исправить:* форматировать строку по шагу графика (день / неделя / месяц), задать
  `interval="preserveStartEnd"` и `minTickGap`.
- **Линии графика белые, а в легенде синяя и зелёная — непонятно, где выручка, а где прибыль.** Цвет
  линий задан как `hsl(var(--chart-N))`, но переменные shadcn заданы в формате `oklch`.
  *Как исправить:* одна константа цвета на серию — и для линии, и для легенды, `var(--chart-N)` без
  `hsl()`.
- **Подписи оси Y переносятся на две строки, верхняя обрезана.** *Как исправить:* увеличить ширину оси.
- **Линии сглажены, поэтому резкий провал продаж в выходные выглядит плавным.** *Как исправить:* тип
  линии `"monotone"` вместо сглаживающего.

## 13. Что улучшил бы в production

- **Индексы под реальные запросы** — по `sold_at` и составные под keyset/рейтинг, подтверждённые
  `EXPLAIN ANALYZE` (ветка `perf`, D11).
- **Кэширование ответов по конкретным датам** — данные read-only и после seed неизменны, ответы можно
  кэшировать по паре дат (не по названию пресета).
- **Отдельный контейнер миграций (C2)** — чтобы код API никогда не выполнял DDL, особенно при
  нескольких экземплярах API.
- **Права БД только на чтение для API** — API ничего не пишет (кроме инициализатора), рантайм-пользователь
  может иметь только `SELECT`.
- **История карточек товаров** — полноценная таблица версий вместо только `version_at`.
- **Наблюдаемость** — OpenTelemetry (трейсы, метрики) поверх уже настроенного structured-логирования
  Serilog и health-checks.
- **CI** — сборка, прогон тестов (backend на Testcontainers, frontend на Vitest) и генерация/проверка
  OpenAPI-документа на каждом пуше.
